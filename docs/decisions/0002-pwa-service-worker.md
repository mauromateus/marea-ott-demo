# 0002. PWA and service worker

## Context

The goal is an installable web app that can later be wrapped (TWA on Android, shells on TV) without rewriting it. It must never get in the way of live playback.

## Decision

- `public/manifest.json`: `display: standalone`, `start_url` and `scope` relative (`.`, see ADR 0004), navy theme and background colors, icons 192 and 512 as separate `any` and `maskable` entries (generated by `scripts/generate-icons.js`). `index.html` links the manifest, `theme-color`, `apple-touch-icon` and the iOS standalone meta tags.
- Service worker through CRA's built-in Workbox **InjectManifest**: `src/service-worker.js`, registered by `src/serviceWorkerRegistration.js` in production only.
  - Precache of the app shell (everything the build emits) except `/config/*.json`.
  - Navigations get the shell from the network first, with the precached `index.html` as fallback (see "Fresh navigations"). Not for URLs that look like files, so `/.well-known/assetlinks.json` is still served by the server.
  - Runtime cache, StaleWhileRevalidate, for same-origin images, fonts and `/config/*.json`.
  - **Never cached or intercepted**: anything on `*.mdstrm.com` (including the Lightning script), HLS/DASH manifests, media segments, and requests with `audio`, `video` or `track` destinations. The rules are a pure function (`src/core/services/ServiceWorker/cacheRules.js`) with tests, and no route matches those requests, so the browser goes straight to the network.
  - Update flow: a `SKIP_WAITING` message handler in the worker; `UpdateToast` shows "New version available" with a Refresh button when a worker is waiting and its version differs from the running page (see "Update toast by version"), and reloads after the new worker takes control.
- Config is excluded from the precache so editing `marea.json` does not wait for a new service worker.

## Fresh navigations

Context: the shell used to be precached and served cache-first, so after a deploy a returning user kept the previous version until they tapped the toast. A deep link to a route that only exists in the new version landed on the old app and fell back to home. The owner wants the latest version whenever there is a connection; the cached copy is only for offline. GitHub Pages serves every file with `Cache-Control: max-age=600`, so even a plain network fetch can return an HTTP-cached `index.html` for up to 10 minutes.

Decision (`src/core/services/ServiceWorker/navigationHandler.js`, wired in `src/service-worker.js` on the same `isNavigationFallback` matcher):

- Not offline: fetch the **shell URL** (`PUBLIC_URL + '/index.html'`, never the navigation URL) with a new non-navigate `Request` using `{ cache: 'no-cache', credentials: 'same-origin' }` (conditional revalidation, so most reloads cost a 304), raced against a 3 s timeout. A `response.ok` is returned as is.
- Network error, timeout, a non-ok response or offline: return the precached shell (`createHandlerBoundToURL`). The fetched HTML is never cached by hand; the precache owns the shell.
- Fetching the shell URL (not the navigation URL) matters on Pages: `/tv` is a 404 there and returns the `404.html` body, while `index.html` answers 200.
- `NetworkFirst({ fetchOptions })` was not used because Workbox ignores `fetchOptions` for navigation requests (`request.mode === 'navigate'`), so the HTTP cache would still be consulted. A fresh `Request` is not a navigation, so its `cache` option is honored.
- Unchanged: precache of the build assets (except `/config/*.json`), runtime caching rules, and nothing on `*.mdstrm.com`, player scripts, HLS/DASH manifests or media segments is intercepted.

## Update toast by version

Context: with fresh navigations the page already runs the newest bundle, but the new worker still installs afterwards and would raise a pointless toast right after a refresh.

Decision: the version identity is the hashed main bundle name (`main.d0945250.js`, `src/core/Utils/getMainBundleName.js`). The worker answers a `GET_VERSION` message over the event's `MessageChannel` port with `{ type: 'VERSION', main }`, read from its own precache manifest. When a worker is waiting, `ServiceWorkerService.handleUpdate` asks it (2 s timeout) and compares with the main bundle of the running page (its script tags):

- Equal: post `SKIP_WAITING` and show no toast. No reload is forced.
- Different, no answer in time, or an old worker without the handler: keep the toast and let the user decide.

Tradeoff: a tab that keeps running old JS while a new worker activates can request old lazy chunks that no longer exist. That is why a differing version still asks the user, and why the silent path is limited to identical bundles.

## Consequences

- Offline, the shell and config load, but live streams do not (by design).
- On a very slow connection the first load can wait up to the 3 s timeout before the precached shell is used. With a connection, the shell is revalidated on every navigation (200 or 304).
- A worker is per origin: each client domain needs its own manifest, icons and worker, served from that domain at the root. See `docs/PORTING.md`.
- A TWA needs `/.well-known/assetlinks.json` served by the real domain (template: `docs/assetlinks.example.json`; placeholders must be replaced).
- Wrong cache rules can break playback, so any change to `cacheRules.js` must keep its tests green and be re-tested on a real device.
- Verified in desktop Chrome against a production build: the worker activates, the precache holds only the app shell, the update toast appears when a new build is deployed and Refresh loads the new version.

## How to test

- `npm test -- --watchAll=false src/tests/core/services` (cache rules, update service).
- `npm run build && npx serve -s build -l 5050`, open `http://localhost:5050`. In DevTools, Application > Service Workers should show an activated worker and Cache Storage should list only app assets. Check the Network tab on `/tv`: the Lightning script and media requests must not say "from ServiceWorker".
- Rebuild and reload to see the update toast (a new build with a different main bundle).
- Fresh navigations: deploy twice with the same tab or installed app open, reload, and watch the Network panel: `index.html` must show 200 or 304 (not "from ServiceWorker" or "from disk cache") and the new version loads with no toast. A deep link to a route added in the second deploy must open that route.
- Offline: in DevTools, Network > Offline, reload: the app still opens from the precached shell.
- No toast right after a fresh reload; the toast appears only when a waiting worker's main bundle differs from the page's.
